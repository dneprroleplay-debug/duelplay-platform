# DuelPlay Finance — Production Foundation

## Цель

Финансовый контур DuelPlay разделяет пользовательский баланс, заблокированные средства, внешний платёжный провайдер и неизменяемый журнал операций.

## Где что хранится

### PostgreSQL на WEB VPS

- `Wallet` — текущий доступный, заблокированный и бонусный баланс.
- `Transaction` — пользовательский ledger с before/after снимками баланса.
- `WalletHold` — резерв средств под матч или вывод.
- `Deposit` — попытки и подтверждения пополнений.
- `Withdrawal` — заявки и состояния выводов.
- `KycVerification` — статус проверки личности и идентификатор дела у KYC-провайдера.
- `PlatformLedgerEntry` — доход/расход платформы: комиссия матча, платёжные комиссии, комиссии вывода и ручные корректировки.
- `WebhookEvent` — идемпотентная регистрация внешних webhook-событий.
- `PaymentReconciliation` — результаты сверки с платёжным провайдером.

### Внешние сервисы

Реальные деньги находятся у платёжного/банковского/финансового провайдера. DuelPlay хранит у себя только необходимый учёт и идентификаторы операций, а не данные банковских карт.

## Денежный цикл матча

1. Создание матча: сумма списывается из `Wallet.balance` и сразу резервируется через `WalletHold(MATCH_STAKE)`.
2. Подключение второго игрока: его ставка проходит тот же reserve-flow.
3. Отмена: ставка возвращается в доступный баланс и hold закрывается как `RELEASED`.
4. Техническая победа/результат: hold закрываются; выигрыш зачисляется победителю; комиссия записывается в `PlatformLedgerEntry(MATCH_COMMISSION)`.
5. Повторная обработка результата не должна выдавать деньги повторно: используются idempotency keys.

## Пополнение

В production пополнение разрешается только после реализации конкретного `PaymentGatewayAdapter`.

Поток:

`checkout -> provider -> signed webhook -> WebhookEvent -> Deposit -> creditWallet -> Transaction(DEPOSIT)`

Браузер пользователя не является источником истины для статуса оплаты.

## Вывод

Поток:

`request -> checks -> debit available -> WalletHold(WITHDRAWAL) -> provider payout -> signed webhook -> COMPLETED или RELEASED`

Проверки включают:

- достаточный доступный баланс;
- account status;
- дневной лимит;
- лимит одной операции;
- KYC, если включён настройкой;
- risk score / manual review;
- идемпотентность заявки.

При успешной выплате withdrawal hold становится `CONSUMED`. При ошибке провайдера средства возвращаются в доступный баланс, а hold становится `RELEASED`.

## Webhook security

- HMAC SHA-256 signature;
- максимальный размер payload;
- обязательная привязка события к провайдеру;
- `provider + externalId` как уникальный ключ;
- fallback external ID = SHA-256 исходного payload;
- повторно обрабатывается только `RECEIVED/FAILED`, событие `PROCESSED` идемпотентно;
- сумма webhook сверяется с ожидаемой суммой депозита/вывода.

## Принципы

- Деньги не хранятся как JS `Number` внутри wallet service.
- PostgreSQL `Decimal(20,4)` используется для денежных значений.
- Денежные изменения происходят внутри транзакций с блокировкой строки кошелька `FOR UPDATE`.
- Нельзя доверять клиентскому запросу для зачисления денег.
- Нельзя хранить номер карты/CVV/PIN.
- Нельзя включать production payments одним boolean-флагом: должен существовать реальный adapter и webhook secret.
- `app/api/admin/route.ts` не изменяется в этой серии изменений.

## Что ещё не активировано

Реальный платёжный провайдер пока не выбран и не подключён. Поэтому production `deposit/withdraw` намеренно возвращают состояние `PAYMENT_GATEWAY_NOT_CONFIGURED` / `PAYMENT_ADAPTER_NOT_IMPLEMENTED` вместо создания фиктивных платежей.

Перед запуском real-money beta нужно отдельно реализовать adapter выбранного провайдера, его signed webhooks, reconciliation и пройти end-to-end тесты на staging.
