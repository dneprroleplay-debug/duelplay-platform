# DuelPlay HUB — этап 1: отчёт по глобальному поиску, вызовам, лигам и аналитике
Дата: 2026-10-28
База: последний доступный архив `duelplay-equipped-banner-rating-sync.zip`. В архиве нет `.git`, поэтому подтвердить фактический HEAD/commit `a63bee1` из этой копии невозможно.

## 1. Глобальный поиск
Проверены `app/search/page.tsx` и `app/api/search/route.ts`.
- API ограничивает запрос 64 символами и возвращает пустые результаты при длине менее 2 символов.
- Поиск ограничен по количеству результатов; выбираются активные, не удалённые и не тестовые аккаунты.
- В поддерживаемых результатах присутствуют игроки, кланы, события, турниры и кейсы.
- Результаты игроков ведут через карточки профиля; API выдаёт данные через явные Prisma `select`.
- Найденный недостаток: страница поиска молча сохраняет старые результаты при HTTP-ошибке, а состояние ошибки не показывается. В этом этапе не менял поведение поиска без отдельного регрессионного UI-теста. Мобильная вёрстка использует адаптивные сетки, но браузерная проверка не выполнялась.
- Локализация поиска в компоненте частично захардкожена на английском. Это подтверждённый долг, не исправленный в этой сборке.

## 2. Вызовы
Изменено:
- `app/api/challenges/route.ts`: GET выдаёт только вызовы текущего пользователя (отправитель или получатель), с `Cache-Control: private, no-store`. Принятие уже принятого вызова повторно возвращает ранее связанный матч вместо создания второго матча/повторного списания.
- `app/challenges/page.tsx`: интерфейс разделён на «Мои вызовы» и отдельное пояснение о том, что публичные предложения матчей текущим API не поддерживаются. Добавлены RU/UA/EN/PL подписи, состояния, кнопки и прямая ссылка `/matches/{matchId}` после принятия. Страница обновляет данные при возвращении вкладки и периодически.
- `app/notifications/page.tsx`: уведомление типа `CHALLENGE` с `payload.challengeId` получает локализованную кнопку «Открыть вызов», ведущую на `/challenges?challenge=...`; страница прокручивает к конкретному вызову.
- `scripts/test-hub-stage1-challenges.mjs`: 17 source-level assertions для приватности списка, статусов/прав, идемпотентности, ссылок, языков, лиг, аналитики и поиска.
- `package.json`: команда `test:hub-stage1-challenges`.

Подтверждённое поведение API: входящие и исходящие личные вызовы; публичная лента вызовов не реализована в GET, поэтому не выдумывал публичные предложения. PATCH требует, чтобы получатель принимал/отклонял PENDING-вызов, а отправитель мог отменить PENDING-вызов. Создание матча выполняется в транзакции и сохраняет `matchId` в вызове. Реальный двухаккаунтный тест и изолированная PostgreSQL-интеграция не запускались.

Остаток: кнопка «Открыть вызов» для уже закрытого/просроченного приглашения показывает его актуальный статус на странице, но полноценный UI-тест двух аккаунтов остаётся обязательным. Тексты ошибок API в ряде случаев остаются английскими.

## 3. Лиги — фактические правила
Подтверждено `lib/leagues.ts` и `app/api/leagues/route.ts`:
- BRONZE: рейтинг ниже 1200; SILVER: от 1200; GOLD: от 1400; DIAMOND: от 1600; ELITE: от 1800.
- Лига рассчитывается по `PlayerStats.rating`. Прогресс считается линейно между порогами текущей и следующей лиги. В ELITE прогресс равен 100%, следующего порога нет.
- `pointsToNext` — разница между текущим рейтингом и следующим порогом; для ELITE — 0.
- Таблица побед/поражений строится отдельно по матчам `REAL`, `FINISHED`, где есть второй игрок и победитель; победы/поражения агрегируются по `winnerId` и `loserId`.
- Серия берётся из `PlayerStats.winStreak`.
- Маршрут не фильтрует матчи по сезону и не использует сезонные сбросы. В этих файлах нет логики повышения рейтинга после каждого матча — это не следует путать с вычислением лиги из уже сохранённого рейтинга.
- Параметры порогов заданы в коде `lib/leagues.ts`; API настроек порогов в рассмотренном маршруте нет.

Пример, следующий из кода: игрок с рейтингом 1350 находится в SILVER, до GOLD (1400) ему не хватает 50 рейтинговых очков, прогресс SILVER→GOLD составляет 75%. Это не означает, что одна победа обязательно даст 50 очков: формула изменения рейтинга находится вне этих функций.

## 4. Аналитика — фактические показатели
Подтверждено `app/api/analytics/route.ts`:
- API требует авторизованного пользователя и запрашивает его собственный `PlayerStats` и его `MatchPlayerStat`; клиент не передаёт чужой userId.
- История ограничена последними 50 записями статистики матчей пользователя, где матч имеет `status=FINISHED` и `economyMode=REAL`, сортировка по `MatchPlayerStat.createdAt` по убыванию.
- `K/D`: kills/deaths, округление до 2 знаков; если deaths=0, возвращается kills.
- `HS%`: headshots/kills × 100, 1 знак; при kills=0 — 0.
- `AVG DMG`: суммарный damage этих максимум 50 записей / число записей; при пустой истории — 0.
- kills/deaths/headshots/damage берутся из агрегированного `PlayerStats`, если он существует; иначе считаются по загруженным последним 50 строкам. Поэтому при наличии PlayerStats эти значения накопительные, а история/averageDamage/bestMap/favouriteWeapon основаны только на выборке последних 50 строк — это важное различие.
- rating, wins, losses, totalDuels, streak и bestStreak берутся из `PlayerStats`. bestMap и favouriteWeapon — наиболее частые значения в выборке; при равенстве применяется алфавитный порядок.
- `ratingHistory` возвращается из `PlayerStats.ratingHistory`; период/частота записи этой истории в этом API не определены.
- Доступ к чужой аналитике через данный маршрут не предоставляется. Административные аналитические маршруты не проверялись как часть пользовательской страницы.

Пример: если в выборке 5 записей, суммарно 20 убийств, 10 смертей, 8 хедшотов и 1500 урона, K/D=2.00, HS%=40.0%, AVG DMG=300.0. Это иллюстрация формул API, не реальные данные аккаунта.
